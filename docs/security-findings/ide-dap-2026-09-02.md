# Security review: `ide-dap` (F5a debugger client)

## Scope

- Reviewed: `crates/dap/**` on worktree `/Users/ivs/rust/ide-worktrees/rust-dap-dev-debugger-f5a`, branch `rust-dap-dev/debugger-f5a`, commit `78a76b5` (just `rev`-approved).
- Declared security-sensitive surface (`CLAUDE.md`): subprocess spawn of a debug adapter, and every DAP response treated as attacker-influenced data (stack frames, source paths, variable values — though `evaluate`/variables are F5b, not in this doc).

**Ruled out, with why:**
- **MITM / Replay / Downgrade / Timing side-channels / Weak randomness** — `crates/dap/Cargo.toml` enables no `net` feature on `tokio` and there is no `std::net`/`tokio::net` usage anywhere in the crate (confirmed by grep). The only transport is stdio to a locally-spawned child process; there is no network surface at all, so these categories don't apply.
- **evaluate / arbitrary expression execution** — confirmed by grep that no `evaluate` request variant exists anywhere in `crates/dap/src` (F5b scope, correctly not implemented here).
- **Cryptography, authN/authZ, multi-tenant state** — not applicable to this crate.

**Live tests actually run** (all via a throwaway harness crate in scratchpad, path-depending on this worktree's `ide-dap` and spawning real `DapClient::start()` instances against a Python "malicious adapter" script speaking the real wire protocol — not just code reading):

1. Deeply nested JSON array (200,000 levels) as an event body.
2. Deeply nested JSON object (200,000 levels) as an event body.
3. A 50,000-entry `threads` response (exceeds `MAX_ARRAY_ITEMS`=10,000, fits under `MAX_CONTENT_LENGTH`).
4. A `stackTrace` response with three path-escape attempts: a symlink created inside the project root pointing to a file outside it, a `../../../../etc/passwd`-style traversal, and a raw absolute `/etc/passwd`.
5. Non-UTF8 / truncated body: `Content-Length: 20` header with only 16 bytes actually sent, adapter process kept alive afterward (no more data, no stream close).
6. `Content-Length: -5` (negative) and `Content-Length: 16777217` (cap+1, no body sent).
7. A flood of 500,000 well-formed tiny `output` events.
8. A flood of 200,000 adapter-initiated reverse requests (`runInTerminal`).

Code-analysis-only (no live test needed — deterministic from the API used): subprocess spawn via `tokio::process::Command::new(command).args(args)` with no shell involved anywhere (`client.rs:140-147`), so command/argument injection via shell metacharacters is not applicable regardless of what a user types into `LanguageConfig::debug_adapter_command`/`_args`.

## Findings

1. **`[DoS] Medium`** — `crates/dap/src/protocol.rs:105` (`AsyncReadExt::read_exact` for the message body) and the header line-reading loop at `protocol.rs:44-70` (`read_line` inside the `.take(MAX_HEADER_BYTES)` wrapper) have no time-based timeout, only a byte-count bound. A debug adapter that sends a `Content-Length` header promising more bytes than it ever actually writes — and then simply keeps its process alive without closing stdout or sending more data — causes `read_exact` to block forever waiting for bytes that never arrive. No `ReadOutcome::Error`/`Eof` is ever produced, so `DapEvent::AdapterExited` never fires.

   **Concrete attack**: adapter capability, no adapter cooperation beyond what any adapter already has (send `Content-Length: 20\r\n\r\n` + 16 bytes, then block on its own stdin instead of exiting). Verified live: harness received `CapabilitiesReceived`/`ReadyForBreakpoints` and then nothing else for 15+ seconds; no `AdapterExited`, no error, no timeout recovery — the read hangs indefinitely for as long as the adapter process stays alive. (The child process itself does get reaped once the *caller* drops the `DapClient` — e.g. app exit — since `request_rx` closing is a separate, working break-out path; the hang is in the session staying stuck while the app keeps running, not a process surviving app exit.)

   **Impact**: `DebugPanel::session` (per `docs/features/debugger.md` §3.5) never transitions back to `None` — the UI has no signal the session is dead, "Stop" (which sends `Disconnect`) still gets written to the adapter's stdin but the confirming `terminated` event or any error can never arrive since the reader task is wedged on the earlier partial read, so the Debug tool window is left showing stale state indefinitely with no way to recover short of the user force-quitting the whole IDE process. A merely *buggy* (not intentionally malicious) adapter that crashes mid-write without closing its pipe — a realistic, non-adversarial scenario, e.g. `codelldb` segfaulting — could trigger the same wedge, not only a deliberate attack.

   **Suggested fix direction**: wrap the header-read loop and the body `read_exact` in `tokio::time::timeout(...)` (a constant analogous to the existing `KILL_TIMEOUT`, but much larger — e.g. tens of seconds, since a legitimately slow/large `variables` response shouldn't be punished) and treat an elapsed timeout the same as `ReadOutcome::Error` — ending the session with `AdapterExited` rather than hanging forever. This is the same fix shape `ide-lsp` should be checked for too, if it has the identical framing code with the same gap (out of this review's scope, but worth flagging to whoever owns that crate).

## Not exploitable / working as intended

- **Deeply nested JSON (array and object, 200,000 levels)**: `serde_json`'s built-in recursion-depth guard rejects both with a clean `"recursion limit exceeded"` error before any stack overflow, live-confirmed (`AdapterExited` after ~100ms in both cases, process never crashed).
- **50,000-entry `threads` array**: `MAX_ARRAY_ITEMS` (10,000) truncation confirmed live — client delivered exactly `Threads(len=10000)`, no unbounded allocation, no slowdown.
- **Path-escape via symlink / `../` traversal / absolute path in a `stackTrace` response**: all three live attempts came back `source: None`. `validate_path`'s canonicalize-then-`starts_with(root)` check holds against a real adversarial adapter, not just the existing unit tests.
- **Oversized/negative `Content-Length`**: both rejected cleanly and immediately (`AdapterExited`), no allocation attempted for the oversized case (rejected before the body buffer is allocated, as designed).
- **500,000-message flood** (well-formed tiny events): max RSS stayed at ~3MB over 15s; the bounded-channel backpressure chain (reader channel cap 8 → event channel cap 64) throttles the adapter's own writes once the caller stops draining, rather than growing memory unbounded.
- **200,000 reverse-request flood**: same result, ~3MB max RSS; each reverse request is declined and forgotten one at a time, no accumulation.
- **Command/argument injection**: not applicable — `tokio::process::Command::new(command).args(args)` never goes through a shell, confirmed by reading `spawn_child` (`client.rs:135-155`).

## Verdict

Findings, highest severity **Medium** (one finding: missing read timeout can wedge a debug session indefinitely on a truncated frame from a malicious or merely crashed adapter).
