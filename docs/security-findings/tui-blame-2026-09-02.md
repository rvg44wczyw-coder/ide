# TUI Blame (T29) — Adversarial Security Review

## 1. Scope

Reviewed: `crates/tui/src/blame_gutter.rs` (new) and the `GitPanel::blame_for`/
`GitPanel::commit_detail` extensions to `crates/tui/src/git_panel.rs`, in
worktree `rust-tui-dev-tui-blame`, branch `rust-tui-dev/tui-blame`, commit
`6f6a17a` (`rev`-approved). Both paths are on `CLAUDE.md`'s declared
security-sensitive list. Also touched by this phase but not independently
re-audited: `crates/tui/src/app.rs`'s `toggle_blame_annotations`/
`click_blame_lane`/`show_blame_for_current_line` (pure key/mouse dispatch and
state, no new I/O) and `crates/tui/src/ui.rs`'s rendering (consumes only
already-sanitized strings from the two files above).

Attack-surface categories from the `hacker` skill checklist, and applicability:

- **Input validation (adversarial)** — applies: repository-sourced author
  names, emails, commit summaries, and bodies are untrusted content
  (`docs/security-findings/git-branches-and-blame-ui-2026-09-01.md`'s
  original finding class for the GUI equivalent). Live-tested.
- **DoS / resource exhaustion** — applies: `git` imposes no hard commit
  message length limit, so a crafted commit body could in principle be
  arbitrarily large before this phase's length caps are applied. Live-tested.
- **Path traversal** — applies to `GitPanel::blame_for`'s
  canonicalize+`strip_prefix` path handling, but this logic is reused
  unchanged from the already-`hacker`-reviewed `ide-ui`/T28 pattern (the
  feature doc, `docs/features/tui-blame.md` §4, states this explicitly:
  "this phase introduces no new path-provenance logic of its own to audit").
  Verified by code reading only, not re-tested live, per the `hacker`
  skill's own guidance to focus on genuinely new surface.
- MITM/Replay/Downgrade/KeyConfusion/Timing/WeakRandomness/SandboxEscape/
  MetadataLeak — ruled out: this diff has no network/IPC handshake, no
  session/protocol state, no key derivation, no timing-sensitive
  comparison, no randomness, and spawns no subprocess or plugin.

Live tests actually run: adversarial-input sanitization and DoS timing
(below). No live network/IPC/subprocess simulation was applicable to this
diff's actual surface.

## 2. Method

`crates/tui/src/blame_gutter.rs` and `crates/tui/src/git_panel.rs` are
private modules (`mod`, not `pub mod`, in `crates/tui/src/lib.rs`), so an
external harness cannot link against them directly. Rather than relying on
code reading alone, `strip_bidi_controls`/`truncate_display`'s function
bodies (and `GitPanel::commit_detail`'s exact composition,
`truncate_display(&strip_bidi_controls(&field), CAP)`) were copied verbatim
into a standalone scratch harness
(`/private/tmp/.../scratchpad/hacker-blame/main.rs`, outside the repo, not
committed) and run against adversarial payloads. This exercises the actual
reviewed algorithm, not a reimplementation. 182 checks run this way, plus
the crate's own existing adversarial unit tests
(`commit_detail_strips_bidi_controls_from_author_and_email`,
`commit_detail_caps_an_unbounded_summary_and_body`,
`annotations_from_blame_strips_bidi_controls_from_author_and_summary`, and
`blame_gutter`'s own bidi/truncation test module) were re-run via
`cargo test -p ide-tui` and confirmed passing (1004/1004).

## 3. Findings

None. All adversarial tests passed.

Specifically verified live, not just read:

1. **[InputValidation]** Every one of the 12 Unicode bidi control
   codepoints this fix targets (`U+202A..=U+202E`, `U+2066..=U+2069`,
   `U+200E`, `U+200F`, `U+061C`), individually prepended to a 400-character
   payload and run through `strip_then_truncate` at cap sizes `{1, 5, 50,
   200, 399, 400, 401}` (84 combinations), never survived into the output,
   and the output never exceeded its cap. Also tested the reversed
   composition order (`truncate_then_strip`) for comparison: both orderings
   fully removed every override codepoint in every case tried — `strip`
   unconditionally scans whatever string it's given, so composition order
   doesn't change the *final* codepoint-presence guarantee for a
   single-codepoint control character (unlike a multi-codepoint escape
   sequence, which this class of character isn't). The codebase's
   documented strip-then-truncate order is still correct to keep as the
   ported convention (matches `ide-ui`'s precedent, and is the composition
   `GitPanel::commit_detail` actually uses), just not empirically
   distinguishable from the alternative for this specific character class
   in the cases tried.
2. **[InputValidation]** A bidi override placed exactly at the truncation
   boundary (`offset ∈ {cap-1, cap, cap+1}` for `cap ∈ {10, 50, 200}`, 9
   cases) — the case most likely to expose an off-by-one or a split
   multi-byte sequence, since `chars()` operates on Unicode scalar values —
   never leaked the override or exceeded the cap.
3. **[InputValidation]** A realistic "Trojan Source"-style payload
   (`"safe-looking-author\u{202E}\u{0000}reversed-payload-that-should-vanish"`)
   run through the real pipeline came out as
   `"safe-looking-author\0reversed-payload-that-should-vanish"` — the
   override is gone; nothing renders reversed. (The embedded NUL byte
   itself survived, since `strip_bidi_controls` only targets bidi-control
   codepoints, not NUL — this is outside this fix's declared scope, no new
   visual-spoofing capability, and NUL handling in a `ratatui::text::Span`
   is a pre-existing, crate-wide characteristic of every text field, not
   something this phase introduces or changes.)
4. **[InputValidation]** `truncate_display`'s char-boundary safety on a
   surrogate-pair-adjacent multi-byte script (mathematical alphanumeric
   symbols, 4 bytes/char in UTF-8) truncated to 5 chars produced exactly 5
   chars with no panic — confirms `chars().take(n)` handles this correctly
   (already covered by the crate's own port of `ide-ui`'s equivalent test,
   re-confirmed independently here).
5. **[DoS]** A crafted commit body of 1MB, 8MB, and 32MB (git itself
   enforces no commit-message length cap, so this is a realistic
   attacker-controlled input from a cloned, untrusted repository) run
   through the full strip-then-truncate pipeline *before* the 4000-char cap
   takes effect completed in 3.7ms, 18.4ms, and 59.3ms respectively — linear
   scaling, no hang, no superlinear blowup. `GitPanel::commit_detail`'s
   caps bound the *output*, not the cost of processing an oversized input,
   but at these sizes (and this scaling) that cost is not a practical DoS
   vector for a single popup render.

## 4. Verdict

Clean.
